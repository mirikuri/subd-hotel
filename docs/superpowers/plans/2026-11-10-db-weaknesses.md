# Минусы проекта QonaqHotels (фокус — СУБД) и порядок исправления

## Context

Запрос: оценить слабые места проекта, главное — база данных. Проект учебный по СУБД
(PostgreSQL + Npgsql без ORM, «целостность — ограничениями БД»). Ниже — что нашёл при чтении
`db/schema.sql`, `db/seed.sql`, `db/reset.sh` и всего кода с SQL, по убыванию важности,
и в каком порядке это чинить.

Что сделано хорошо и трогать не надо: EXCLUDE-ограничения на пересечение дат (номера, сезоны,
смены), параметризованные запросы везде, транзакции на связанных изменениях, ловля SQLSTATE 23xxx
вместо «SELECT перед INSERT», атомарный счётчик неудачных входов.

## Минусы

### 1. Половина схемы — мёртвая (самое заметное на защите)
В схеме 20 таблиц. К 9 из них приложение не делает ни одного запроса: `seasons`, `rates`,
`stays`, `service_categories`, `services`, `service_orders`, `shifts`, `loyalty_cards`,
`audit_log`. Они заполняются только из `seed.sql`, а в `Models/` для них лежат неиспользуемые классы.
Следствия:
- цена брони нигде не считается, хотя есть тарифы и сезоны;
- заселение (`stays`) не создаётся — статус «заселён» это просто пункт выпадающего списка;
- `audit_log` никем не пишется (нет ни триггеров, ни кода); в нём к тому же нет старых/новых значений.

### 2. В БД нет ничего, кроме таблиц
0 представлений, 0 функций, 0 триггеров, 0 процедур, 0 ролей/GRANT. Для проекта, где «главное —
СУБД», это главный пробел: вся логика — в C#. `appsettings.json` ссылается на роль `gosti_app`,
но её нигде не создают; `reset.sh` и тесты работают под суперпользователем `postgres`.

### 3. Один факт хранится в двух местах, и БД их не связывает
Согласованность держится только на коде страниц; прямой `UPDATE` в psql её ломает.
- `bookings.check_in_plan/check_out_plan` ↔ `booking_rooms.date_from/date_to`.
- `bookings.hotel_id` ↔ отель номера: БД позволяет привязать к брони номер чужого отеля
  (проверка только в `INSERT … SELECT` в `Bookings/Create.cshtml.cs`, `Edit.cshtml.cs`).
- `bookings.status = 'отменена'` ↔ `booking_rooms.is_active = false`.
- `positions.role` ↔ `users.role` (копируется в `EmployeeAccounts.SyncRoleAsync`);
  у `positions.role` нет CHECK, у `users.role` есть.
- «Уволен» = `employees.dismissal_date` + `users.is_active` + `locked_until = now() + 100 лет`.
- `rooms.status`: «занят»/«свободен» никто не обновляет, код читает только «ремонт».
  Это производное состояние, которое хранится и врёт.

### 4. Не хватает ограничений
- Нет `CHECK ((status = 'отменена') = (cancel_reason IS NOT NULL))` — только в коде.
- `guests_count` не сверяется с `room_types.capacity`.
- Бронь может существовать без единого номера (`RoomId` необязателен) — она ничего не резервирует.
- Переходы статусов не ограничены: «завершена» → «новая» проходит.
- `stays`: можно два открытых заселения на одну строку `booking_rooms`; сотрудник может быть из другого отеля.
- `service_orders`: услуга может быть из отеля, отличного от отеля брони.
- Нет UNIQUE на `room_types.name`, `service_categories.name`, `hotels.name`
  (при этом `seed.sql` соединяет по `hotels.name`).
- `guests`: нет `CHECK ((login IS NULL) = (password_hash IS NULL))`; данные человека и учётной
  записи в одной таблице, хотя для сотрудников учётки вынесены в `users`.
- Ограничения безымянные, а `Data/DbErrors.cs` опирается на авто-имена (`bookings_check`,
  `employees_check`): добавление второго CHECK в таблицу молча сломает сообщения об ошибках.

### 5. Модель цен
- Тариф = тип номера × сезон, без отеля: «Люкс» в 3★ и 5★ стоит одинаково. Нет валюты при сети в 4 странах.
- Цена брони не хранится (решение из спеки от 2026‑11‑03): изменение тарифа задним числом
  меняет стоимость прошлых броней. При этом в `service_orders` цена фиксируется (`price_at_order`) — непоследовательно.
- Сезоны — конкретные даты на год‑1…год+2 из `seed.sql`; дальше тарифов просто нет, и ничто
  не гарантирует, что сезоны идут без дыр и у каждого типа есть тариф.

### 6. Индексы и запросы
- Явных индексов два (`lower(login)`). На столбцах внешних ключей индексов нет:
  `bookings.guest_id`, `bookings.hotel_id`, `booking_rooms.booking_id`, `stays.booking_room_id`,
  `employees.hotel_id/position_id`, `service_orders.booking_id` и др. Каждая проверка
  RESTRICT/CASCADE при удалении родителя — последовательный просмотр.
- `UNIQUE (login)` дублирует уникальный индекс по `lower(login)` (в `guests` и `users`).
- Списки (`Bookings/Index`, `Guests/Index`) без LIMIT/пагинации; поиск `lower(x) LIKE '%…%'`
  без `pg_trgm`; сортировка по `booking_date` без индекса; `AdminLists.Guests` грузит всех гостей в `<select>`.
- Нигде нет `EXPLAIN ANALYZE` — заявление в `BookingQueries.cs` про GiST-индекс ничем не подтверждено.

### 7. Типы и время
- Вперемешку `timestamp` (`stays`, `service_orders`, `shifts`, `audit_log`) и `timestamptz`
  (`bookings`, `guests`, `users`), причём `timestamp … DEFAULT now()`.
- «Сегодня» берётся из часов сервера приложения (`Data/Clock.cs`), а `CURRENT_DATE`/`now()` — из БД;
  блокировка входа сравнивается с `DateTime.UtcNow` в коде. У отелей в разных странах нет часового пояса.
- Статусы — кириллические строки в CHECK, продублированные в `Models/DomainValues.cs`
  и ещё раз литералами в `Bookings/Index.cshtml.cs`.

### 8. Эксплуатация
- Нет миграций: `schema.sql` только CREATE, любое изменение схемы = `DROP DATABASE` (`reset.sh`).
- Тестам нужен живой PostgreSQL под `postgres` с пустым паролем; чистят за собой `DELETE`-ами,
  а не откатом транзакции. Про брони и EXCLUDE (ядро проекта) тестов нет.
- Нет защиты от потерянного обновления: форму брони открыли двое — второй молча затирает первого.
- `ON DELETE CASCADE` на `shifts` и `users` от `employees`, `SET NULL` в `audit_log.user_id` —
  история теряется при физическом удалении.

### 9. Код вокруг БД (вторично)
SQL размазан по ~25 PageModel, чтение по номерам столбцов (`r.GetInt32(0)`), один и тот же запрос
шапки брони повторён трижды, экранирование LIKE скопировано. Публичный поиск (`Search.cshtml.cs`)
в БД не ходит вообще.

## Рекомендуемый порядок исправления

1. **Ограничения и имена** (`db/schema.sql`, `Data/DbErrors.cs`): дать имена всем CHECK/EXCLUDE,
   добавить недостающие из п.4; составной FK `booking_rooms(room_id, hotel_id) → rooms(id, hotel_id)`
   вместе с `bookings(id, hotel_id)`, чтобы номер чужого отеля был невозможен на уровне БД.
2. **Убрать дубли** (п.3): `rooms.status` оставить только для «ремонт/уборка» (или булев флаг),
   занятость — представлением; `is_active` выставлять триггером от `bookings.status`;
   `users.role` брать из `positions` через представление либо синхронизировать триггером.
3. **Серверные объекты**: представление свободных номеров и загрузки, функция цены брони
   по `rates`/`seasons`, триггер аудита на `audit_log` (пользователь через `SET LOCAL app.user_id`),
   роль `gosti_app` с GRANT в отдельном `db/roles.sql`.
4. **Оживить мёртвые таблицы** или удалить их: заселение/выезд пишут `stays`, цена считается
   по тарифам и фиксируется в брони. То, что не будет использоваться, — убрать из схемы и `Models/`.
5. **Индексы**: на FK-столбцы и `bookings(booking_date)`, убрать дублирующие UNIQUE;
   приложить `EXPLAIN ANALYZE` до/после на объёме, сгенерированном `generate_series`.
6. **Типы**: всё время — `timestamptz`; один источник «сегодня».
7. **Тесты** на брони: пересечение дат, гонка двух вставок, чужой отель, отмена освобождает номер.

Пункты 1, 2, 5, 6 меняют только `db/schema.sql` + точечно код; 3 и 4 — самые объёмные.

## Проверка

- `db/reset.sh -y gosti_test` проходит без ошибок (схема + seed в одной транзакции).
- В psql вручную: вставка номера чужого отеля, отмена без причины, второе открытое заселение —
  каждая должна падать с именованным ограничением.
- `dotnet test` (нужна база `gosti_test`); новые тесты на брони зелёные.
- `EXPLAIN ANALYZE` запроса свободных номеров и списка броней на раздутых данных показывает Index Scan.
