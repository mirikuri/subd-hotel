# Поиск номера, заявки с сайта, справочники и цены в долларах — дизайн

Дата: 2026-11-10.

## Зачем

1. **Сайт.** Страница `/Search` сейчас заглушка («Поиск номеров скоро заработает»), хотя форма поиска на главной уже ведёт туда. Гость должен найти свободный номер, увидеть цену и отправить заявку на бронь.
2. **Справочники.** Отели, типы номеров, номера, сезоны с тарифами и услуги сейчас меняются только через `db/seed.sql`. Администратору нужны страницы для их редактирования. Заодно таблицы получают больше полезной информации (площадь, кровать, удобства, вид из окна, время заезда и т. д.).
3. **Деньги.** Цены сейчас в тенге. Все цены переводятся в доллары США.
4. **Роли.** Всё это должно уважать разделение ролей: гость, ресепшен, бухгалтер, админ.

Проект учебный по СУБД: SQL прямо в коде (Npgsql, без ORM), целостность обеспечивается ограничениями БД, ошибки ограничений переводятся в сообщения через `Data/DbErrors.cs`.

## Цели

- Гость ищет на сайте по городу, датам и числу гостей и видит доступные типы номеров с ценой за ночь и за весь период.
- Вошедший гость отправляет заявку, и в БД сразу создаётся бронь «новая» с источником «сайт» и назначенным номером.
- У гостя есть страница «Мои брони»: он видит свои брони и может отменить заявку в статусе «новая».
- На главной в карточках типов номеров показано «от $N за ночь».
- В админке пять справочников с просмотром, добавлением, правкой и удалением: отели, типы номеров (с удобствами), номера, сезоны и тарифы, услуги.
- Все цены хранятся и показываются в долларах.
- Каждая страница доступна только нужным ролям; гость в админку не попадает вообще.

## Не цели

- Шахматка и формы брони в админке (`Admin/Bookings/Create`, `Edit`) не меняются. Номер для брони администратор по-прежнему выбирает в шахматке.
- Оплаты на сайте нет. Заявка — это бронь «новая», дальше её ведёт ресепшен.
- Мультивалютности и курсов нет: одна валюта, USD.
- Тарифы остаются «тип номера × сезон» без разделения по отелям.
- Гостей поимённо, детей отдельно, Excel-отчёт из спеки от 2026-11-03 здесь не делаются.
- Фото номеров из справочника не загружаются: картинки остаются файлами в `wwwroot/img`.

## Анти-цели (провал, даже если «работает»)

- Через сайт можно занять один номер двумя бронями на пересекающиеся даты, в том числе при одновременной отправке двух заявок.
- Сайт показывает тип номера как доступный, а заявка на него не проходит, хотя никто его не занял (расхождение запроса поиска с EXCLUDE-ограничением).
- Гость открывает любую страницу `/Admin/*` или видит и отменяет чужую бронь.
- Ресепшен или бухгалтер может сделать то, что разрешено только админу, отправив POST в обход интерфейса.
- В интерфейсе остался знак тенге или цена без «$».

## Роли и доступ

Роли сотрудников: `админ`, `ресепшен`, `бухгалтер` (`Models/DomainValues.cs`, CHECK `users_role_check`). Роль гостя `гость` ставит `RegisterLogin.cshtml.cs` в claim роли.

**Найденная дыра, чинится в этой работе.** `Program.cs` закрывает папку `/Admin` через `AuthorizeFolder("/Admin")`, а это требует только входа, не роли. `Admin/Index.cshtml.cs` помечен просто `[Authorize]`, поэтому вошедший гость открывает `/admin`. Нужно:

- добавить политику `RequireStaff` (любая из трёх ролей сотрудника) и закрыть ею папку `/Admin` целиком;
- добавить политику `RequireGuest` (роль `гость`) для заявок и «Моих броней»;
- добавить политику `RequireAccountant` (бухгалтер или админ) для правки цен.

Матрица доступа:

| Что | гость | ресепшен | бухгалтер | админ |
|---|---|---|---|---|
| `/Search`, главная (смотреть) | да | да | да | да |
| Отправить заявку, «Мои брони» | да | — | — | — |
| Шахматка, брони, гости (как сейчас) | — | да | — | да |
| Справочники: просмотр | — | да | да | да |
| Номера: сменить только статус (свободен / уборка / ремонт) | — | да | — | да |
| Сезоны и тарифы, услуги: правка цен | — | — | да | да |
| Отели, типы номеров, удобства, номера, сезоны, услуги: добавить / удалить / править всё | — | — | — | да |
| Сотрудники, пользователи, должности (как сейчас) | — | — | — | да |

Атрибут политики ставится на `PageModel` (как сейчас), а не прячется только в меню. Если на одной странице есть действия разных уровней (например, `Rooms/Edit`: статус может менять ресепшен, остальное — админ), обработчик POST проверяет роль сам и игнорирует поля, которые этой роли менять нельзя.

Меню админки (`Shared/_AdminLayout.cshtml`) показывает пункты по роли: бухгалтер не видит «Шахматку» и «Брони», ресепшен и бухгалтер не видят «Сотрудников», «Пользователей» и «Должности». Пункт «Справочники (скоро)» становится рабочим и ведёт на страницу-оглавление справочников. Пункт «Поиск номера (скоро)» убирается из меню: подбор номера в админке — это шахматка.

## Изменения схемы

Всё в `db/schema.sql` (миграций нет, база пересоздаётся `db/reset.sh`), данные — в `db/seed.sql`. Новые ограничения получают явные имена, и эти имена добавляются в `DbErrors.ByConstraint`.

```sql
-- hotels: правила заселения и описание
ALTER TABLE hotels ADD
    check_in_time  time NOT NULL DEFAULT '14:00',
    check_out_time time NOT NULL DEFAULT '12:00',
    email          varchar(120),
    description    text,
    CONSTRAINT hotels_name_key UNIQUE (name);

-- room_types: площадь и кровать, уникальное название
ALTER TABLE room_types ADD
    area_m2  numeric(5,1) CONSTRAINT room_types_area_check CHECK (area_m2 > 0),
    bed_type varchar(30)  CONSTRAINT room_types_bed_type_check
             CHECK (bed_type IN ('односпальная', 'двуспальная', 'две односпальные', 'king-size')),
    CONSTRAINT room_types_name_key UNIQUE (name);

-- справочник удобств и связь «тип номера — удобство» (многие ко многим)
CREATE TABLE amenities (
    id   int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name varchar(60) NOT NULL CONSTRAINT amenities_name_key UNIQUE,
    icon varchar(40)            -- имя значка Bootstrap Icons, например 'wifi'
);
CREATE TABLE room_type_amenities (
    room_type_id int NOT NULL REFERENCES room_types(id) ON DELETE CASCADE,
    amenity_id   int NOT NULL REFERENCES amenities(id)  ON DELETE RESTRICT,
    PRIMARY KEY (room_type_id, amenity_id)
);

-- rooms: вид из окна
ALTER TABLE rooms ADD
    view varchar(20) CONSTRAINT rooms_view_check CHECK (view IN ('город', 'парк', 'двор', 'горы'));

-- service_categories: уникальное название
ALTER TABLE service_categories ADD CONSTRAINT service_categories_name_key UNIQUE (name);

-- services: описание и признак «продаётся»
ALTER TABLE services ADD
    description text,
    is_active   boolean NOT NULL DEFAULT true;

-- bookings: пожелания гостя из заявки
ALTER TABLE bookings ADD
    guest_comment varchar(500);
```

(В `schema.sql` это пишется прямо в `CREATE TABLE`, а не через `ALTER`. Выше `ALTER` только для наглядности, что добавилось.)

**Деньги.** Столбцы `rates.price_per_night`, `services.price`, `service_orders.price_at_order` остаются `numeric(10,2)` и с этой работы означают доллары США. Это фиксируется комментарием в `schema.sql` (`COMMENT ON COLUMN ... IS 'USD'`). В `seed.sql` базовые цены за ночь: Стандарт 50, Комфорт 65, Полулюкс 85, Люкс 130, Семейный 105, Бизнес-люкс 160. Сезонные коэффициенты прежние, округление до целого доллара (`round(..., 0)`). Услуги: завтрак 12, ужин 25, доставка в номер 5, сауна 16, массаж 30, трансфер 18, стирка 4 за кг, с прежними коэффициентами по звёздности, округление до доллара.

`seed.sql` также заполняет новые столбцы правдоподобными значениями: площадь и кровать каждого типа, 8–10 удобств и их привязку к типам, вид из окна у номеров, время заезда и выезда у отелей.

## Часть 1. Сайт: поиск и заявка

### Поиск (`/Search`)

Параметры: город (`cities.id`, обязательный), заезд, выезд, гостей (1–6). Форма на главной (`Pages/Index.cshtml`, `#search-form`) уже отправляет GET на `/search`; её поля приводятся к этим параметрам, а список городов берётся из БД (он уже грузится в `IndexModel.Cities`).

Проверки: выезд позже заезда; заезд не раньше сегодня; не дальше года вперёд; не больше 30 ночей. «Сегодня» берётся из `Clock.Today`.

Результат — карточки «отель × тип номера», где есть хотя бы один свободный номер:
- отель (звёзды, адрес), тип номера, вместимость, площадь, кровать, значки удобств;
- «осталось N номеров», если свободных 3 или меньше;
- цена: средняя за ночь и сумма за период, например «$130 / ночь · $390 за 3 ночи»;
- кнопка «Забронировать».

**Свободный номер** — то же условие, что в `Admin/Bookings/BookingQueries.AvailableRoomsSql`: номер не на ремонте и у него нет активной строки `booking_rooms` с пересекающимся `daterange(date_from, date_to, '[)')`. Плюс `room_types.capacity >= гостей`. Условие занятости выносится в одно место (общий SQL-фрагмент или класс в `Data/`), и его используют и админка, и сайт, чтобы они не разошлись.

**Цена за период** — сумма по ночам: для каждой ночи `d` из `generate_series(заезд, выезд - 1 день)` берётся `rates.price_per_night` типа номера и сезона, где `d BETWEEN seasons.date_start AND date_end`. Если хотя бы на одну ночь тарифа нет, тип номера в результатах не показывается: продать его без цены нельзя. Всё считается одним SQL-запросом.

Поиск открыт всем, включая невошедших.

### Заявка

Кнопка «Забронировать» ведёт на страницу подтверждения `/Booking/Request` с параметрами отель, тип номера, даты, гостей. Невошедший гость перенаправляется на `/Register-Login?returnUrl=...` и после входа или регистрации возвращается обратно. Сейчас `RegisterLogin` после входа всегда делает `Redirect("/")`; нужно поддержать `returnUrl` и принимать только локальные адреса (`Url.IsLocalUrl`). Сотрудник, вошедший под своей учёткой, заявку отправить не может: страница требует роль `гость`.

Страница подтверждения показывает то же, что карточка поиска, итоговую сумму и поле «Пожелания» (до 500 символов). Цена на этой странице пересчитывается заново, а не берётся из адреса.

**Отправка (POST)** — одна транзакция:
1. Повторные проверки дат и числа гостей; гость `is_active`.
2. Ограничение от спама: у гостя не больше 3 броней со статусом «новая» и источником «сайт» с заездом в будущем. Иначе сообщение «У вас уже 3 необработанные заявки».
3. Найти первый свободный номер нужного типа в отеле (тот же общий запрос, `ORDER BY floor, room_number LIMIT 1`).
4. `INSERT INTO bookings` (`guest_id` из claim, `hotel_id`, даты, `source = 'сайт'`, `guest_comment`; статус по DEFAULT «новая») и `INSERT INTO booking_rooms` (`guests_count` = гостей).
5. Если `booking_rooms` упал с `23P01` (номер только что заняли), откатиться к точке сохранения и взять следующий свободный номер. До 3 попыток, затем сообщение «Свободных номеров этого типа на эти даты не осталось».

Гарантию «один номер — одна бронь» по-прежнему даёт только EXCLUDE-ограничение. Код не блокирует таблицы и не проверяет занятость перед вставкой как замену ограничению.

После успеха — переход на «Мои брони» с сообщением «Заявка №N отправлена, администратор свяжется с вами».

### Мои брони (`/Booking/My`)

Только роль `гость`. Список своих броней (`guest_id` из claim, никогда из параметров запроса): №, отель, тип и номер комнаты, даты, гостей, сумма по тарифам, статус. Кнопка «Отменить» есть только у статуса «новая».

Отмена — одна транзакция: `UPDATE bookings SET status = 'отменена', cancel_reason = 'Отменено гостем' WHERE id = @id AND guest_id = @me AND status = 'новая'`. Если затронута 1 строка, выполняется `UPDATE booking_rooms SET is_active = false WHERE booking_id = @id`. Иначе сообщение «Бронь уже обработана, отменить нельзя».

В шапке сайта для вошедшего гостя в выпадающем меню появляется пункт «Мои брони».

### Главная

В карточках типов номеров (`Pages/Index.cshtml`, `#rooms`) показывается «от $N за ночь»: минимальный `price_per_night` этого типа среди сезонов, которые пересекаются с ближайшими 12 месяцами. Площадь и значки удобств — там же. Если тарифа нет, цена не показывается.

## Часть 2. Справочники в админке

Новая папка `Pages/Admin/Catalogs/` с оглавлением `Index` (пять карточек). Каждый справочник — `Index` / `Create` / `Edit` / `Delete` в том же стиле, что существующие `Admin/Positions` и `Admin/Guests`: SQL в PageModel, `FilterBarModel` + `_FilterBar` для поиска в списке, строки таблицы в partial-представлении, ошибки ограничений через `DbErrors`.

1. **Отели** — название, город (каскадный выбор страна → город, как в фильтре броней), адрес, звёзды, телефон, e-mail, время заезда и выезда, описание. Удаление запрещает FK (`ON DELETE RESTRICT` от номеров, броней, сотрудников, услуг), сообщение через `DbErrors.DescribeDelete`.
2. **Типы номеров** — название, вместимость, площадь, кровать, описание, удобства (галочки). Удобства сохраняются в той же транзакции, что и тип: удалить лишние строки `room_type_amenities`, вставить новые. Здесь же отдельная маленькая страница или блок «Удобства» (название, значок): добавление, переименование, удаление; удаление занятого удобства запрещает FK.
3. **Номера** — фильтр по отелю, этажу, типу, статусу. Поля: отель, тип, номер, этаж, вид, статус. Ресепшен в `Edit` видит форму, где редактируется только статус; админ — всё. Удаление номера, на который есть брони, запрещает FK. Смена типа номера на тип с меньшей вместимостью, чем `guests_count` будущих броней, не проверяется (моё решение: это случай для админа, БД это не ловит).
4. **Сезоны и тарифы** — список сезонов (название, с, по). Пересечение сезонов запрещает уже существующий EXCLUDE в `seasons`; ему дать имя `seasons_no_overlap` и сообщение «Сезон пересекается с другим сезоном». Страница сезона показывает таблицу «тип номера → цена за ночь, $», которую можно править целиком; сохранение — одна транзакция `INSERT ... ON CONFLICT (room_type_id, season_id) DO UPDATE`, пустое поле удаляет тариф. Создавать и удалять сезоны может только админ, менять цены — бухгалтер и админ.
5. **Услуги** — фильтр по отелю и категории. Поля: отель, категория, название, описание, цена в $, единица, «продаётся». Бухгалтер меняет только цену и «продаётся», админ — всё. Категории правятся на той же странице маленьким списком (только админ). Услугу, которая уже есть в `service_orders`, удалить нельзя (FK RESTRICT); вместо этого её снимают с продажи.

## Часть 3. Деньги в интерфейсе

Один помощник форматирования (например, `Models/Money.cs`, метод `Usd(decimal)`) выводит `$1,250` (без копеек, если сумма целая, иначе `$12.50`). Все места, где выводится цена, используют его. Поля ввода цен в справочниках подписаны «$» и принимают точку как разделитель. В интерфейсе не должно остаться знака тенге (`₸`) и «тг».

## Решения, принятые мной (проверь)

- Номер назначается сразу при заявке, а не администратором потом: так EXCLUDE защищает и сайт.
- Заявку может отправить только вошедший гость: в брони нужен гость с номером документа.
- Не больше 3 необработанных заявок с сайта у одного гостя.
- Тип номера без тарифа хотя бы на одну ночь в поиске не показывается.
- Не больше 30 ночей и не дальше года вперёд.
- Цена брони в БД не хранится, считается по текущим тарифам (как в спеке от 2026-11-03).
- Ресепшен может менять только статус номера, бухгалтер — только цены и «продаётся» у услуг; всё остальное в справочниках — только админ.
- Пункт меню «Поиск номера (скоро)» убирается: в админке номер подбирают в шахматке.
- Базовые цены в долларах из раздела «Деньги».

## Что оставлено исполнителю

- Вёрстка карточек поиска и страниц справочников в стиле существующих `site.css` и `admin.css`. В рабочей копии есть незакоммиченные правки пользователя (`_Layout.cshtml`, `_AdminLayout.cshtml`, `site.css`, `wwwroot/js/searchable-select.js`); их нельзя затирать, новые правки идут поверх.
- Где именно держать общий SQL «свободный номер» и «цена за период».
- Набор удобств и значков, точные площади и виды из окна в seed.

## Проверка

- `db/reset.sh -y gosti_test`, затем `dotnet test` — всё зелёное.
- Новые тесты на `gosti_test`:
  - поиск не возвращает тип, все номера которого заняты на эти даты, и возвращает его на соседние даты;
  - цена за период через границу сезонов равна ручной сумме;
  - две заявки на последний свободный номер типа: одна проходит, вторая получает другой номер или сообщение, но не 500 и не двойную бронь;

- Вручную: заявка с сайта появляется в шахматке и списке броней как «новая · сайт»; на главной видно «от $50 за ночь»; ни на одной странице нет тенге.
