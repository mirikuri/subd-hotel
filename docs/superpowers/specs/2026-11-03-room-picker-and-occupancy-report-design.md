# Выбор номера в брони и Excel-отчёт о загрузке — дизайн

Дата: 2026-11-03. Ветка: `feat/admin-validation-search`.

## Зачем

1. **Выбор номера.** В форме брони сейчас один длинный `<select>` со всеми свободными номерами отеля (до 40 строк). Администратору нужен удобный фильтр, а не список. Главное требование — один номер нельзя занять двумя бронями на одни даты; это уже гарантирует ограничение `booking_rooms_room_id_daterange_excl`, его сохраняем как единственный источник истины.
2. **Гости брони.** Нужно знать, сколько гостей в номере, и зарегистрировать каждого взрослого (18+), а не только того, на кого оформлена бронь.
3. **Отчёт.** Из шахматки — выгрузка в Excel загрузки отелей за период: по отелям, по типам номеров, будни/выходные, по дням, по сезонам, по источникам.

Проект — учебный по СУБД: вся логика расчётов в SQL прямо в коде (Npgsql, без ORM), целостность — ограничениями БД.

## Цели

- Плиточный подбор свободного номера с фильтрами, ценой за период и кнопкой «Первый свободный».
- Взрослые гости брони регистрируются поимённо, дети — количеством.
- Предупреждение, если у гостя уже есть пересекающаяся бронь.
- Скидка по карте лояльности и итог брони перед сохранением.
- Отчёт `.xlsx` о загрузке по параметрам.

## Не цели

- Шахматку как способ выбора номера не меняем (номер там выбирается кликом по ячейкам и передаётся в форму).
- Каскадный фильтр списка броней (страна → город → отель) не меняем.
- Цену брони в БД не храним — она вычисляется по тарифам при показе (см. «Решения»).
- Диаграммы в Excel не рисуем.
- Регистрация детей поимённо не нужна.

## Анти-цели (провал, даже если «работает»)

- Возможность записать один номер на две брони с пересекающимися датами — хоть через форму, хоть через гонку двух администраторов.
- Проверка занятости в коде, расходящаяся с EXCLUDE-ограничением (номер показан свободным, а INSERT падает, или наоборот).
- Отчёт, цифры которого нельзя проверить SQL-запросом к базе.

## Изменения схемы (согласованы с пользователем)

```sql
-- Сколько детей (до 18) в номере; взрослые — строки booking_guests
ALTER TABLE booking_rooms ADD COLUMN children_count smallint NOT NULL DEFAULT 0
    CHECK (children_count >= 0);

-- Зарегистрированные взрослые гости номера в брони
CREATE TABLE booking_guests (
    id              int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    booking_room_id int NOT NULL REFERENCES booking_rooms(id) ON DELETE CASCADE,
    guest_id        int NOT NULL REFERENCES guests(id) ON DELETE RESTRICT,
    UNIQUE (booking_room_id, guest_id)
);
```

В `db/schema.sql` правится `CREATE TABLE booking_rooms` (новый столбец) и добавляется `booking_guests` после него; `db/seed.sql` заполняет `booking_guests` (основной гость каждой брони + для части броней второй взрослый) и `children_count`. Живая база пересоздаётся `db/reset.sh` (в ней сейчас только seed-данные).

Смысл существующих полей:
- `bookings.guest_id` — основной гость (плательщик), всегда первый в `booking_guests` первого номера брони.
- `booking_rooms.guests_count` — всего гостей в номере = взрослые + дети; держится в коде равным `count(booking_guests) + children_count`.

## Часть 1. Форма брони (Create и Edit)

### Поток

1. Отель, даты заезда/выезда (как сейчас, flatpickr).
2. **Гости:** поле «Взрослых» (≥1) и «Детей» (≥0). Для каждого взрослого — строка: поиск по ФИО или номеру документа среди `guests` (AJAX, 10 совпадений) либо «Новый гость» (ФИО, документ, дата рождения обязательны; телефон, страна — по желанию). Первый взрослый — основной гость брони.
3. **Фильтры номера:** тип (кнопки с числом свободных номеров этого типа), этаж (любой/конкретный). Вместимость фильтруется автоматически: показываются только номера, у которых `room_types.capacity >= взрослые + дети`.
4. **Плитки** свободных номеров: номер, этаж, тип, сумма за период и цена за ночь. Клик выбирает номер. Кнопка «Первый свободный» выбирает любую подходящую плитку (какую — не важно, пользователю всё равно). «Без номера» остаётся возможным, как сейчас.
5. **Предупреждения** (не блокируют сохранение): у кого-то из зарегистрированных взрослых есть другая бронь с активным номером, пересекающаяся по датам, в любом отеле — «У гостя Х уже есть бронь №N в отеле Y на dd.mm–dd.mm».
6. **Итог** под плитками: «Люкс 304 · 3 ночи · 2 взрослых + 1 ребёнок · 195 000 ₸ · скидка gold −10% · к оплате 175 500 ₸».

При открытии из шахматки (`?roomId&hotelId&dateFrom&dateTo`) выбранный номер уже отмечен, фильтры сброшены так, чтобы он был виден.

### Правила

- **Свободный номер** — то же условие, что в `BookingQueries.LoadAvailableRoomsAsync`: нет активной строки `booking_rooms` с пересекающимся `daterange(...,'[)')`, номер не на ремонте. Новый запрос плиток расширяет его (тип, этаж, вместимость, цена), а не пишет заново.
- **Возраст 18+** проверяется в коде по `guests.birth_date` на дату заезда (CHECK в БД не может смотреть в другую таблицу). Взрослый без даты рождения — ошибка формы «Укажите дату рождения». Гость младше 18 в строке взрослых — ошибка.
- **Цена за период** — сумма по ночам: для каждой ночи `d` из `generate_series(check_in, check_out - 1)` берётся `rates.price_per_night` типа номера и сезона, где `d BETWEEN date_start AND date_end`. Если хотя бы для одной ночи тарифа нет — плитка показывает «нет тарифа», номер всё равно можно выбрать.
- **Скидка** по уровню карты основного гостя: silver 5%, gold 10%, platinum 15% (константы в коде). Только для показа в итоге.
- **Сохранение** — одна транзакция: `bookings` → `booking_rooms` (с `guests_count`, `children_count`) → новые гости `guests` → `booking_guests`. Ошибки ограничений (EXCLUDE, UNIQUE документа нового гостя) — сообщением в форме через `DbErrors`, как сейчас.
- **Edit:** те же блоки; замена номера/дат — существующий `SyncRoomAsync`; состав гостей синхронизируется (удалить лишние `booking_guests`, вставить новые). Основной гость меняется вместе с первой строкой взрослых.

### Новые обработчики (Bookings/Create, Bookings/Edit)

- `OnGetRoomTilesAsync(hotelId, dateFrom, dateTo, roomTypeId?, floor?, people, excludeBookingId)` → JSON плиток + счётчики по типам.
- `OnGetGuestSearchAsync(q)` → JSON до 10 гостей (id, ФИО, документ, дата рождения).
- `OnGetOverlapsAsync(guestIds[], dateFrom, dateTo, excludeBookingId)` → JSON предупреждений.
- `OnGetLoyaltyAsync(guestId)` → уровень карты или null.

## Часть 2. Excel-отчёт о загрузке (Chess)

### Где и параметры

Кнопка «Отчёт в Excel» в панели шахматки открывает небольшую форму: период с–по (по умолчанию текущий месяц), отели (все/выбранные), типы номеров (все/выбранные). Обработчик `OnGetReportAsync` в `Pages/Admin/Chess/Index.cshtml.cs` отдаёт файл `zagruzka_<с>_<по>.xlsx`. Доступ — как у шахматки (`RequireReceptionist`).

### Определения

- **Доступная номеро-ночь** — пара (номер, дата) для каждого номера выбранных отелей/типов и каждой даты периода. Номера на ремонте считаются доступными (истории ремонтов в БД нет).
- **Проданная номеро-ночь** — (номер, дата), для которой есть активная строка `booking_rooms` с `date_from <= дата < date_to`. Отменённые брони не учитываются (их номера неактивны). Будущие брони («новая», «подтверждена») учитываются — это загрузка «на руках».
- **Выручка ночи** — тариф типа номера в сезоне этой даты (`rates`); без тарифа — 0 и пометка в листе «Сводка».
- **Загрузка** = проданные / доступные. **ADR** = выручка / проданные. **RevPAR** = выручка / доступные. **ALOS** = проданные номеро-ночи / число броней, заезд которых в периоде.
- **Выходная ночь** — ночь с пятницы на субботу и с субботы на воскресенье (`extract(isodow FROM дата) IN (5, 6)`); остальные — будние.
- **Отмены** — брони со статусом «отменена», у которых `check_in_plan` в периоде.

Все показатели считаются в SQL: основа — `generate_series` по датам × `rooms` с `LEFT JOIN booking_rooms` по попаданию даты в период, затем `GROUP BY` под каждый лист. Excel только оформляет результат.

### Листы

1. **Сводка** — по отелям и итог по сети: номеров, доступно, продано, загрузка %, выручка, ADR, RevPAR, ALOS, броней, отмен, % отмен; шапка с параметрами отчёта и датой формирования.
2. **По типам номеров** — отель × тип: те же показатели.
3. **Будни и выходные** — отель × тип × (будни | выходные): доступно, продано, загрузка, ADR, RevPAR.
4. **По дням** — строки даты (выходные залиты цветом), столбцы отели, ячейка — загрузка %; цветовая шкала зелёный→красный.
5. **По сезонам** — сезоны, пересекающие период: отель × сезон, загрузка и выручка.
6. **Источники** — источник брони: броней, номеро-ночей, выручка, доля.
7. **Брони** — плоский список броней, пересекающих период: №, отель, номер, тип, гость, заезд, выезд, ночей в периоде, статус, источник, выручка в периоде.

Форматы: проценты `0.0%`, деньги `# ##0 ₸`, закреплённая шапка, автоширина, автофильтр на табличных листах.

## Решения, принятые мной (проверь)

- Цена брони не сохраняется в БД — показывается по текущим тарифам. Если потребуется фиксировать цену на момент брони, нужен столбец в `bookings` (как `price_at_order` у услуг).
- Скидки 5/10/15% по уровням и только для показа.
- Предупреждение о пересечении — по всем отелям сети, не блокирует сохранение.
- Будущие брони входят в загрузку отчёта; номера на ремонте — доступны.
- Выходные — ночи пт→сб и сб→вс.
- Excel без диаграмм, вместо них цветовые шкалы.

## Что оставлено исполнителю

- Вёрстка плиток и формы гостей в стиле существующей админки (Bootstrap + `admin.css`).
- Разбиение кода: отчёт — отдельный класс в `Pages/Admin/Chess/` (SQL + сборка книги), не раздувать `Index.cshtml.cs`.
- Тесты: SQL расчёта загрузки на `gosti_test` (известные данные seed → известные числа), проверка 18+, синхронизация `guests_count`.
